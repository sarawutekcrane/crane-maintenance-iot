======================================================================
PROJECT CONTEXT
======================================================================

Act as a senior embedded systems engineer, IoT firmware architect, backend integration engineer, and heavy-equipment electronics engineer.

This project is an ESP32-based IoT platform for mobile cranes and related heavy equipment. The final system must monitor and manage:

- ignition state,
- engine-running state,
- engine operating hours,
- PTO state,
- PTO operating hours,
- vehicle speed pulse,
- calculated vehicle speed,
- calculated travel distance / odometer,
- engine RPM pulse,
- analog sensor values,
- battery/system voltage,
- fuel level when supported,
- temperature when supported,
- hydraulic pressure when supported,
- GPS/GNSS position,
- network state,
- device health,
- firmware version,
- configuration version,
- offline queued data,
- structured device events,
- remote command status,
- future model-specific emergency output.

CORE RULE:

MEASUREMENT, COUNTER ACCUMULATION, AND LOCAL EVENT RECORDING MUST NEVER DEPEND ON INTERNET AVAILABILITY.

Prototype system:

ESP32 Device
    ->
Backend / API
    ->
Google Sheets Data Service
    ->
Thai-language Web Application

Production system:

ESP32 Device
    ->
Backend / Device Transport Layer
    ->
PostgreSQL
    ->
Thai-language Web Application

Important architecture rules:

1. The browser must NEVER communicate directly with the ESP32.
2. The ESP32 must NEVER write directly to Google Sheets.
3. The ESP32 communicates only with the backend/device transport layer.
4. Google Sheets is a prototype database only.
5. PostgreSQL will become the production source of truth.
6. ESP32 communication must not depend on the backend database technology.
7. All user-facing Web pages must be in Thai.
8. Backend/API/database/device field names and stable technical codes may remain in English.
9. The backend owns fleet/business logic, PM rules, lifetime rules, alerts, permissions, and workflow.
10. The ESP32 owns reliable local measurement, counters, local event generation, offline buffering, and device communication.

======================================================================
GLOBAL SOFTWARE RULES
======================================================================

The firmware must be:
- modular,
- non-blocking,
- testable,
- recoverable,
- configurable,
- fault tolerant,
- storage aware,
- network independent,
- future ESP32-S3 ready.

Do not:
- create one monolithic .ino file,
- use long blocking delay() calls,
- place network calls in timing-critical input code,
- write counters to flash every second,
- hard-code vehicle-specific calibration in core logic,
- hard-code future emergency ON/OFF timings before source data is supplied,
- silently remove previously working functions,
- change frozen interfaces from earlier phases without explicit approval.

Prefer:
- explicit interfaces,
- clear ownership of each module,
- state machines,
- hardware timers / esp_timer where appropriate,
- PCNT or suitable ESP32 peripherals for pulse counting,
- versioned configuration,
- persistent queues,
- structured logging,
- compile-time feature flags for incomplete future hardware.

======================================================================
PHASE-INDEPENDENCE RULE
======================================================================

This project is intentionally divided into independent coding phases.

The purpose is to make each phase:
- buildable,
- testable,
- reviewable,
- stable before the next phase begins.

Once a phase is accepted, its public interfaces and behavior become FROZEN.

Later phases must extend the system through predefined interfaces instead of rewriting earlier modules.

If a later phase discovers that an earlier frozen interface is insufficient:

1. STOP.
2. Explain the exact limitation.
3. Propose a backward-compatible extension or a versioned interface.
4. Do NOT silently refactor the old phase.
5. Wait for user approval before changing the frozen contract.

Minimal integration wiring is allowed, but completed core logic from earlier phases must not be redesigned without approval.

REQUIRED CLAUDE CODE WORKFLOW
======================================================================

5. Update README / phase notes / CHANGELOG as appropriate.

The user will return the Phase Result Report for external review before authorizing the next phase.

B. Long-Run Testing

Perform/define:
- 24+ hour bench run,
- repeated input transitions,
- continuous pulse injection,
- intermittent Internet,
- server outage,
- repeated reconnect,
- queue growth/clear,
- repeated controlled reboot.

C. Power-Cycle Testing

Verify:
- counters never regress,
- queue survives as designed,
- config survives,
- stale commands do not execute.

D. Storage / Flash Review

Review:
- write frequency,
- wear risk,
- queue capacity,
- corruption recovery,
- storage-full behavior.

E. Watchdog / Fault Injection

Inject:
- sensor missing,
- ADC missing,
- network failure,
- backend failure,
- storage warning,
- GPS invalid,
- invalid configuration.

F. Calibration Verification

Compare:
- speed pulse vs reference speed,
- calculated distance vs reference distance,
- engine runtime vs trusted reference meter,
- PTO runtime vs controlled reference timing.

Do not invent calibration values.

G. ESP32-S3 Migration Review

Identify:
- hardware-specific code,
- pin mapping changes,
- peripheral changes,
- library compatibility,
- memory differences,
- OTA partition considerations.

Core logic should remain unchanged.

- command list,
