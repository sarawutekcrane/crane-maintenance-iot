======================================================================
PROJECT CONTEXT
======================================================================

Act as a senior embedded systems engineer, IoT firmware architect, backend integration engineer, and heavy-equipment electronics engineer.

This project is an ESP32-based IoT platform for mobile cranes and related heavy equipment. The final system must monitor and manage:

- ignition state,
- engine-running state,
- engine operating hours,
- PTO state,
- PTO operating hours,
- vehicle speed pulse,
- calculated vehicle speed,
- calculated travel distance / odometer,
- engine RPM pulse,
- analog sensor values,
- battery/system voltage,
- fuel level when supported,
- temperature when supported,
- hydraulic pressure when supported,
- GPS/GNSS position,
- network state,
- device health,
- firmware version,
- configuration version,
- offline queued data,
- structured device events,
- remote command status,
- future model-specific emergency output.

CORE RULE:

MEASUREMENT, COUNTER ACCUMULATION, AND LOCAL EVENT RECORDING MUST NEVER DEPEND ON INTERNET AVAILABILITY.

Prototype system:

ESP32 Device
    ->
Backend / API
    ->
Google Sheets Data Service
    ->
Thai-language Web Application

Production system:

ESP32 Device
    ->
Backend / Device Transport Layer
    ->
PostgreSQL
    ->
Thai-language Web Application

Important architecture rules:

1. The browser must NEVER communicate directly with the ESP32.
2. The ESP32 must NEVER write directly to Google Sheets.
3. The ESP32 communicates only with the backend/device transport layer.
4. Google Sheets is a prototype database only.
5. PostgreSQL will become the production source of truth.
6. ESP32 communication must not depend on the backend database technology.
7. All user-facing Web pages must be in Thai.
8. Backend/API/database/device field names and stable technical codes may remain in English.
9. The backend owns fleet/business logic, PM rules, lifetime rules, alerts, permissions, and workflow.
10. The ESP32 owns reliable local measurement, counters, local event generation, offline buffering, and device communication.

======================================================================
GLOBAL SOFTWARE RULES
======================================================================

The firmware must be:
- modular,
- non-blocking,
- testable,
- recoverable,
- configurable,
- fault tolerant,
- storage aware,
- network independent,
- future ESP32-S3 ready.

Do not:
- create one monolithic .ino file,
- use long blocking delay() calls,
- place network calls in timing-critical input code,
- write counters to flash every second,
- hard-code vehicle-specific calibration in core logic,
- hard-code future emergency ON/OFF timings before source data is supplied,
- silently remove previously working functions,
- change frozen interfaces from earlier phases without explicit approval.

Prefer:
- explicit interfaces,
- clear ownership of each module,
- state machines,
- hardware timers / esp_timer where appropriate,
- PCNT or suitable ESP32 peripherals for pulse counting,
- versioned configuration,
- persistent queues,
- structured logging,
- compile-time feature flags for incomplete future hardware.

======================================================================
PHASE-INDEPENDENCE RULE
======================================================================

This project is intentionally divided into independent coding phases.

The purpose is to make each phase:
- buildable,
- testable,
- reviewable,
- stable before the next phase begins.

Once a phase is accepted, its public interfaces and behavior become FROZEN.

Later phases must extend the system through predefined interfaces instead of rewriting earlier modules.

If a later phase discovers that an earlier frozen interface is insufficient:

1. STOP.
2. Explain the exact limitation.
3. Propose a backward-compatible extension or a versioned interface.
4. Do NOT silently refactor the old phase.
5. Wait for user approval before changing the frozen contract.

Minimal integration wiring is allowed, but completed core logic from earlier phases must not be redesigned without approval.

PHASE 8 OBJECTIVE
======================================================================

Implement the future emergency-related digital output using the exact model-specific fixed ON/OFF timing supplied by the user.

This signal is conceptually serial-like because it uses timed digital ON/OFF transitions, but it is NOT assumed to be standard UART, CAN, or another standard protocol unless the supplied source proves otherwise.

Each crane model has a FIXED timing pattern.

The timing is controlled engineering data, not a freely user-editable Web parameter.

======================================================================
IMPLEMENTATION SEQUENCE
======================================================================

STEP 1 - Source analysis only

Before writing the physical-output implementation:
- extract all timings,
- create a human-readable timing table,
- identify model,
- identify source functions,
- identify repeat logic,
- identify idle/final state,
- list ambiguities.

STOP for user review if anything is unclear.

STEP 2 - Approved profile

Represent the supplied behavior as:

profile_id
model_id
profile_revision
firmware_compatibility
fixed timing steps
idle state
repeat rule
final state
validation status

The individual timing values must not be remotely editable by ordinary configuration.

STEP 3 - Simulation

Use the existing EmergencyOutputManager interface from Phase 1.

Simulation must print:
- model ID,
- profile ID,
- revision,
- step number,
- ON/OFF state,
- expected duration,
- measured duration if available,
- completion/failure.

Do not energize physical output yet.

STEP 4 - Timing verification

Compare simulation/runtime timing against the original supplied source.

Produce a timing comparison table.

STEP 5 - Physical bench output

Only after user approval:
- assign the approved test GPIO,
- enable physical bench mode,
- measure with oscilloscope/logic analyzer.

Do not connect to crane control electronics until electrical interface is separately verified.

STEP 6 - Command integration

Use the reserved safety-critical command path.

Require:
- command_id,
- explicit model/profile match,
- short TTL,
- anti-replay,
- execution ACK,
- result,
- audit event.

STEP 7 - Feedback

If hardware feedback input is not yet defined:
keep feedback status NOT_AVAILABLE.

Do not treat output pin state as proof of machine action.

======================================================================
SAFETY COMMAND RULES
======================================================================

1. Expired command never executes.
2. Wrong-model profile never executes.
3. Missing profile never executes.
4. Invalid profile never executes.
5. Duplicate command must not repeat the physical sequence unexpectedly.
6. Old command must not automatically execute after reconnect.
7. Old command must not automatically execute after reboot.
8. Physical output returns to defined approved idle state.
9. The waveform engine must not stop pulse counting/counters.
10. No remote engine start is included.

======================================================================
TIMING ENGINE
======================================================================

Do not use long delay() chains.

Use a deterministic non-blocking method such as:
- esp_timer,
- hardware timer,
- timestamp-driven state machine,
- another appropriate ESP32 mechanism.

The selected method must be justified against the timing resolution required by the user-supplied source.

======================================================================
SAFETY BOUNDARY
======================================================================

This software output is a secondary control layer until proven otherwise.

OEM hardwired safety functions remain independent.
