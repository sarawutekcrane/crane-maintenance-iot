======================================================================
PROJECT CONTEXT
======================================================================

Act as a senior embedded systems engineer, IoT firmware architect, backend integration engineer, and heavy-equipment electronics engineer.

This project is an ESP32-based IoT platform for mobile cranes and related heavy equipment. The final system must monitor and manage:

- ignition state,
- engine-running state,
- engine operating hours,
- PTO state,
- PTO operating hours,
- vehicle speed pulse,
- calculated vehicle speed,
- calculated travel distance / odometer,
- engine RPM pulse,
- analog sensor values,
- battery/system voltage,
- fuel level when supported,
- temperature when supported,
- hydraulic pressure when supported,
- GPS/GNSS position,
- network state,
- device health,
- firmware version,
- configuration version,
- offline queued data,
- structured device events,
- remote command status,
- future model-specific emergency output.

CORE RULE:

MEASUREMENT, COUNTER ACCUMULATION, AND LOCAL EVENT RECORDING MUST NEVER DEPEND ON INTERNET AVAILABILITY.

Prototype system:

ESP32 Device
    ->
Backend / API
    ->
Google Sheets Data Service
    ->
Thai-language Web Application

Production system:

ESP32 Device
    ->
Backend / Device Transport Layer
    ->
PostgreSQL
    ->
Thai-language Web Application

Important architecture rules:

1. The browser must NEVER communicate directly with the ESP32.
2. The ESP32 must NEVER write directly to Google Sheets.
3. The ESP32 communicates only with the backend/device transport layer.
4. Google Sheets is a prototype database only.
5. PostgreSQL will become the production source of truth.
6. ESP32 communication must not depend on the backend database technology.
7. All user-facing Web pages must be in Thai.
8. Backend/API/database/device field names and stable technical codes may remain in English.
9. The backend owns fleet/business logic, PM rules, lifetime rules, alerts, permissions, and workflow.
10. The ESP32 owns reliable local measurement, counters, local event generation, offline buffering, and device communication.

======================================================================
GLOBAL SOFTWARE RULES
======================================================================

The firmware must be:
- modular,
- non-blocking,
- testable,
- recoverable,
- configurable,
- fault tolerant,
- storage aware,
- network independent,
- future ESP32-S3 ready.

Do not:
- create one monolithic .ino file,
- use long blocking delay() calls,
- place network calls in timing-critical input code,
- write counters to flash every second,
- hard-code vehicle-specific calibration in core logic,
- hard-code future emergency ON/OFF timings before source data is supplied,
- silently remove previously working functions,
- change frozen interfaces from earlier phases without explicit approval.

Prefer:
- explicit interfaces,
- clear ownership of each module,
- state machines,
- hardware timers / esp_timer where appropriate,
- PCNT or suitable ESP32 peripherals for pulse counting,
- versioned configuration,
- persistent queues,
- structured logging,
- compile-time feature flags for incomplete future hardware.

======================================================================
PHASE-INDEPENDENCE RULE
======================================================================

This project is intentionally divided into independent coding phases.

The purpose is to make each phase:
- buildable,
- testable,
- reviewable,
- stable before the next phase begins.

Once a phase is accepted, its public interfaces and behavior become FROZEN.

Later phases must extend the system through predefined interfaces instead of rewriting earlier modules.

If a later phase discovers that an earlier frozen interface is insufficient:

1. STOP.
2. Explain the exact limitation.
3. Propose a backward-compatible extension or a versioned interface.
4. Do NOT silently refactor the old phase.
5. Wait for user approval before changing the frozen contract.

Minimal integration wiring is allowed, but completed core logic from earlier phases must not be redesigned without approval.

======================================================================
REQUIRED CLAUDE CODE WORKFLOW
======================================================================

Before coding this phase:

1. Inspect the repository.
2. Read README, configuration files, existing source, tests, and previous phase result notes.
3. Verify the prerequisite phase is complete.
4. List existing frozen interfaces that this phase will use.
5. List files that will be added.
6. List any existing files that require minimal integration changes.
7. List all TBD values.
8. Present a short implementation plan.
9. Then implement ONLY this phase.

After coding this phase:

1. Build/compile the project.
2. Fix compile errors.
3. Run or clearly define all acceptance tests for this phase.
4. Do not claim PASS for a test that was not actually performed.
5. Update README / phase notes / CHANGELOG as appropriate.
6. Produce the required Phase Result Report.
7. STOP. Do not start the next phase.

The user will return the Phase Result Report for external review before authorizing the next phase.

======================================================================
SCOPE
======================================================================

A. GPS/GNSS

If GPS hardware/module is supplied, implement through a location-provider interface.

Store:
- latitude,
- longitude,
- fix valid,
- fix quality if available,
- satellites if available,
- GPS timestamp,
- last valid fix time.

Never report an invalid fix as valid.

B. Event Location

Attach valid location to important events when available:
- ENGINE_START,
- ENGINE_STOP,
- selected faults,
- server-requested status.

No continuous route history is required in this phase unless explicitly requested.

C. GPS_REFRESH

Activate the Phase 5 command if GPS exists.

D. Cellular Transport Abstraction

Production intention:
- 4G/LTE primary,
- Wi-Fi secondary.

Exact modem:
TBD unless user supplies it.

If modem hardware is not known:
- implement interface/state machine and compile-safe placeholder,
- do not invent modem AT commands,
- do not fake connectivity.

E. Network Selection Policy

Prepare configurable policy:
CELLULAR_PRIMARY_WIFI_SECONDARY

without changing telemetry/event code.

F. Field Health

Strengthen:
- brownout/reset reason logging,
- last successful server contact,
- queue growth warning,
- storage warning,
- time sync health,
- GPS health,
- network transport health.

G. Long Disconnect Behavior

Test hours/distance/pulses while network is unavailable for an extended bench period.

H. Emergency Output

Still disabled unless Phase 8 prerequisites are met.

======================================================================
OUT OF SCOPE
======================================================================

Do not implement:
- arbitrary cellular driver without known hardware,
- full fleet tracking route history,
- OTA,
- real emergency waveform.

======================================================================
PHASE 6 ACCEPTANCE TESTS
======================================================================

1. Valid GPS fix is reported correctly.
2. Invalid GPS fix is clearly invalid.
3. Engine event includes GPS only when valid.
4. GPS failure does not stop counters.
5. Wi-Fi failure does not reset device.
6. Transport abstraction does not alter telemetry schema.
7. If cellular hardware is absent, placeholder compiles and clearly reports NOT_AVAILABLE.
8. Extended network outage does not lose local counters/events.
9. Network recovery clears backlog correctly.

======================================================================
PHASE 6 EXIT GATE
======================================================================

Device is ready for controlled field pilot communication testing without requiring changes to Phases 1-5.
