======================================================================
PROJECT CONTEXT
======================================================================

Act as a senior embedded systems engineer, IoT firmware architect, backend integration engineer, and heavy-equipment electronics engineer.

This project is an ESP32-based IoT platform for mobile cranes and related heavy equipment. The final system must monitor and manage:

- ignition state,
- engine-running state,
- engine operating hours,
- PTO state,
- PTO operating hours,
- vehicle speed pulse,
- calculated vehicle speed,
- calculated travel distance / odometer,
- engine RPM pulse,
- analog sensor values,
- battery/system voltage,
- fuel level when supported,
- temperature when supported,
- hydraulic pressure when supported,
- GPS/GNSS position,
- network state,
- device health,
- firmware version,
- configuration version,
- offline queued data,
- structured device events,
- remote command status,
- future model-specific emergency output.

CORE RULE:

MEASUREMENT, COUNTER ACCUMULATION, AND LOCAL EVENT RECORDING MUST NEVER DEPEND ON INTERNET AVAILABILITY.

Prototype system:

ESP32 Device
    ->
Backend / API
    ->
Google Sheets Data Service
    ->
Thai-language Web Application

Production system:

ESP32 Device
    ->
Backend / Device Transport Layer
    ->
PostgreSQL
    ->
Thai-language Web Application

Important architecture rules:

1. The browser must NEVER communicate directly with the ESP32.
2. The ESP32 must NEVER write directly to Google Sheets.
3. The ESP32 communicates only with the backend/device transport layer.
4. Google Sheets is a prototype database only.
5. PostgreSQL will become the production source of truth.
6. ESP32 communication must not depend on the backend database technology.
7. All user-facing Web pages must be in Thai.
8. Backend/API/database/device field names and stable technical codes may remain in English.
9. The backend owns fleet/business logic, PM rules, lifetime rules, alerts, permissions, and workflow.
10. The ESP32 owns reliable local measurement, counters, local event generation, offline buffering, and device communication.

======================================================================
GLOBAL SOFTWARE RULES
======================================================================

The firmware must be:
- modular,
- non-blocking,
- testable,
- recoverable,
- configurable,
- fault tolerant,
- storage aware,
- network independent,
- future ESP32-S3 ready.

Do not:
- create one monolithic .ino file,
- use long blocking delay() calls,
- place network calls in timing-critical input code,
- write counters to flash every second,
- hard-code vehicle-specific calibration in core logic,
- hard-code future emergency ON/OFF timings before source data is supplied,
- silently remove previously working functions,
- change frozen interfaces from earlier phases without explicit approval.

Prefer:
- explicit interfaces,
- clear ownership of each module,
- state machines,
- hardware timers / esp_timer where appropriate,
- PCNT or suitable ESP32 peripherals for pulse counting,
- versioned configuration,
- persistent queues,
- structured logging,
- compile-time feature flags for incomplete future hardware.

======================================================================
PHASE-INDEPENDENCE RULE
======================================================================

This project is intentionally divided into independent coding phases.

The purpose is to make each phase:
- buildable,
- testable,
- reviewable,
- stable before the next phase begins.

Once a phase is accepted, its public interfaces and behavior become FROZEN.

Later phases must extend the system through predefined interfaces instead of rewriting earlier modules.

If a later phase discovers that an earlier frozen interface is insufficient:

1. STOP.
2. Explain the exact limitation.
3. Propose a backward-compatible extension or a versioned interface.
4. Do NOT silently refactor the old phase.
5. Wait for user approval before changing the frozen contract.

Minimal integration wiring is allowed, but completed core logic from earlier phases must not be redesigned without approval.

======================================================================
SCOPE
======================================================================

A. Network Abstraction

Implement Phase 1 network interface using Wi-Fi.

Keep abstraction suitable for future cellular transport.

Expose:
- connected state,
- network type,
- signal strength,
- local IP where useful,
- last connection result.

B. HTTPS Backend Client

Implement a server client that is independent from Google Sheets.

Do not embed spreadsheet IDs or row numbers.

C. API Version

Use an explicit:
api_version

D. Telemetry

Periodically upload:

device identity
vehicle identity
timestamp / time quality
ignition
engine running
PTO
engine hours
PTO hours
speed
distance / odometer
RPM when valid
analog values when valid
firmware version
actual config version
queue depth
network info
device uptime
reset reason

Only transmit valid values.

E. Event Upload

Upload DeviceEvent records independently from periodic telemetry.

Important events should be queued immediately.

F. Device Health

Upload:
- uptime,
- reset reason,
- heap,
- storage status,
- queue depth,
- network status,
- signal strength,
- time sync state,
- firmware/config versions,
- sensor fault summary,
- last successful upload.

G. Offline Queue

Mandatory durable queue.

Every queued record needs:
- unique ID,
- sequence number,
- record type,
- timestamp or monotonic ordering,
- payload,
- retry metadata.

When offline:
- continue measurement,
- continue events,
- queue data.

On reconnect:
- upload oldest first,
- require server ACK,
- remove only acknowledged record,
- continue until backlog clears.

H. Duplicate Protection

Design for at-least-once delivery.

Use event_id / record_id / sequence number so the backend can reject duplicates safely.

I. Time Synchronization

Implement NTP when online.

Support:
TIME_NOT_SYNCED
TIME_ESTIMATED
TIME_SYNCED

Do not block core functions waiting for time.

J. Backend Contract Documentation

Document request/response JSON for:
- telemetry upload,
- event upload,
- device health upload,
- server ACK.

K. Emergency Output

No command execution in this phase.

Only telemetry may report:
emergency_feature_state = DISABLED / NOT_CONFIGURED.

======================================================================
PHASE 4 ACCEPTANCE TESTS
======================================================================

1. Device uploads telemetry when server is reachable.
2. Engine/PTO counters continue if Wi-Fi is disabled.
3. Events queue while offline.
4. Telemetry can queue while offline according to policy.
5. Reboot preserves required queued records.
6. Reconnect uploads backlog oldest-first.
7. Records remain queued until ACK.
8. Duplicate resend does not corrupt backend data.
9. Backend outage does not cause device reboot loop.
10. Slow HTTPS call does not stop pulse counting.
11. Google Sheets-specific logic is absent from firmware.
12. API schema is documented and versioned.

======================================================================
PHASE 4 EXIT GATE
======================================================================

The device must be demonstrably useful offline and synchronize correctly afterward.

After acceptance, communication transport/API boundaries are frozen.
