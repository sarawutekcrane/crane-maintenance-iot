Crane Fleet Maintenance, IoT Monitoring, Inspection, Repair, Parts, Equipment, and Device Management Platform

======================================================================
2. CORE ARCHITECTURE
======================================================================

Prototype:

Thai Web Application
    ->
Backend API
    ->
Domain / Service Layer
    ->
Repository Interface
    ->
Google Sheets Repository

Production:

Thai Web Application
    ->
Backend API
    ->
Domain / Service Layer
    ->
Repository Interface
    ->
PostgreSQL Repository

Rules:

1. The browser must never access Google Sheets directly.
2. ESP32 devices must never write directly to Google Sheets.
3. Web and device clients communicate through Backend/API services.
4. Google Sheets is a prototype database only.
5. PostgreSQL will be the production Single Source of Truth.
6. Domain/business logic must not depend on Google Sheets formulas.
7. Domain/business logic must not depend on Google Sheets row numbers.
8. Replacing Google Sheets with PostgreSQL must not require rewriting normal Web workflows.
9. Files/media are stored outside relational tables; database stores metadata/storage_ref.

======================================================================
3. BACKEND IS AUTHORITATIVE
======================================================================

The backend/domain layer is authoritative for:

- PM due/overdue,
- PM remaining hours,
- PM remaining distance,
- calendar maintenance due,
- part lifetime due,
- remaining part lifetime,
- part usage accumulation,
- component transfer usage,
- certificate expiry,
- alert generation,
- device offline calculation,
- configuration sync status,
- remote command status,
- repair workflow status,
- inspection/finding workflow status.

Frontend pages display authoritative backend results.

Dashboard, Vehicle Detail, alerts, and reports must use the same domain services.

Do not independently reimplement the same PM/lifetime formula in multiple frontend pages.

8. INSPECTION
======================================================================

-> Detail page
-> ตรวจเช็ค
-> Complete checklist
-> ส่งผลการตรวจ

Inspection item may contain:

- title,
- inspection point,
- reference image,
- inspection method,
- acceptance standard,
- instructions,
- PASS,
- FAIL,
- N/A,
- remark,
- inspection photo.

Reference Image:
master image that explains what/where to inspect.

Inspection Photo:
evidence from the actual inspection.

These are separate concepts.

Checklist definitions are revision-controlled.

======================================================================
11. PART TRACKING MODES
======================================================================

The platform must NOT require registration of every physical part on every vehicle from the beginning.

Support:

NONE
No individual lifetime tracking.

CONSUMABLE
Recorded when consumed during PM/repair.

POSITION_LIFETIME
Tracked by vehicle/position without unique physical instance for every unit.

INSTANCE_TRACKED
A physical reusable/transferable/high-value component with unique part_instance_id.

Same part name with different specification/size must be able to use separate part_id values.

======================================================================
12. INCREMENTAL PART REGISTRATION
======================================================================

Create part_instance only when it becomes necessary, for example:

- transfer between vehicles,
- replacement,
- start of lifetime tracking,
- high-value component,
- safety-critical component,
- reusable/repairable component.

Historical usage state:

KNOWN
PARTIAL
UNKNOWN

If unknown, do not estimate.

======================================================================
13. TRANSFERABLE COMPONENTS
======================================================================

Lifetime/usage follows the physical component.

Example:

Cylinder A
200/2
-> 200/1
-> IN_REPAIR
-> 200/2

Store usage segments with:

- part_instance_id,
- vehicle_id,
- component_id,
- position,
- installed_at,
- baseline counters,
- removed_at,
- ending counters,
- calculated usage,
- source work/event.

Time in IN_REPAIR does not accumulate vehicle operating hours.

======================================================================
14. REPAIR VS OVERHAUL
======================================================================

Normal repair does NOT reset lifetime automatically.

A major overhaul may start a new lifetime cycle only when an approved business rule defines it as a reset.

Old lifetime cycles remain in history.

30. MODEL-SPECIFIC EMERGENCY OUTPUT
======================================================================

The future ESP32 emergency-related output is a fixed ON/OFF timed sequence that may differ by crane model.

The user will provide authoritative existing code/timing later.

Rules:

- do not guess timing,
- do not allow ordinary Web editing of individual timing values,
- Web/backend may store approved profile metadata,
- model/profile compatibility must be enforced,
- actual waveform execution belongs to ESP32 firmware,
- physical feedback is separate from output activation.

MOBILE-FIRST / RESPONSIVE WEB REQUIREMENT
======================================================================

The Web Application must be designed for practical use on mobile phones first, while also supporting tablets and desktop browsers.

The system will be used in operational environments where users may scan a QR code beside a crane or machine and immediately perform inspection, repair reporting, PM review, photo upload, or status checking.

Therefore, mobile usability is a core requirement, not an optional responsive enhancement.

DESIGN PRINCIPLES
=================

1. Use a mobile-first responsive layout.

2. All primary workflows must be fully usable on common smartphone screen sizes.

3. Do not require horizontal scrolling for normal operational pages.

4. Tables that are too wide for mobile must automatically transform into:
   - stacked cards,
   - expandable rows,
   - mobile detail blocks,
   - or another touch-friendly layout.

5. Primary action buttons must be easy to tap with one hand.

6. Touch targets should be sufficiently large and separated to reduce accidental presses.

7. Important actions should remain easy to reach without excessive scrolling.

8. Forms must use mobile-friendly input controls.

9. Avoid tiny text, crowded tables, and desktop-only interaction patterns.

10. Do not rely on hover behavior.

11. Navigation must be suitable for:
   - smartphone,
   - tablet,
   - desktop.

12. The application must support both portrait and landscape orientation where practical.

13. The UI must remain readable when the browser zoom level or device font scaling is increased.

14. Loading, error, offline, empty, and confirmation states must also be mobile-friendly.

15. Camera/photo workflows must work naturally on mobile devices.

16. QR-based navigation must open directly into a mobile-optimized Vehicle Detail or Equipment Detail page.

17. Sticky actions may be used where appropriate for important mobile workflows, such as:
   - submit inspection,
   - save repair report,
   - add photo,
   - create repair,
   - acknowledge alert.

18. Destructive or safety-sensitive actions must not be placed where they can easily be triggered accidentally.

19. Safety-critical remote commands require an intentionally separated confirmation flow and must not be exposed as a simple one-tap mobile control.

20. All mobile pages remain fully in Thai for user-facing content.
