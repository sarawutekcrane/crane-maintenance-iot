SYSTEM REQUIREMENTS BASELINE
Crane Fleet Maintenance, IoT Monitoring, Inspection, Repair, Parts, Equipment, and Device Management Platform
Revision 02

IMPORTANT
=========

Claude Code MUST read this file before implementing every Web/API phase.

This file describes the complete target system.
A phase file describes only the subset to implement now.

No phase may silently contradict, delete, or weaken this baseline.

======================================================================

ALL USER-FACING WEB CONTENT MUST BE IN THAI.

This includes:

- menus,
- page titles,
- tabs,
- buttons,
- labels,
- forms,
- help/instruction text,
- validation messages,

- confirmations,

======================================================================
2. CORE ARCHITECTURE
======================================================================

Prototype:

Thai Web Application
    ->
Backend API
    ->
Domain / Service Layer
    ->
Repository Interface
    ->
Google Sheets Repository

Production:

Thai Web Application
    ->
Backend API
    ->
Domain / Service Layer
    ->
Repository Interface
    ->
PostgreSQL Repository

Rules:

1. The browser must never access Google Sheets directly.
2. ESP32 devices must never write directly to Google Sheets.
3. Web and device clients communicate through Backend/API services.
4. Google Sheets is a prototype database only.
5. PostgreSQL will be the production Single Source of Truth.
6. Domain/business logic must not depend on Google Sheets formulas.
7. Domain/business logic must not depend on Google Sheets row numbers.
8. Replacing Google Sheets with PostgreSQL must not require rewriting normal Web workflows.
9. Files/media are stored outside relational tables; database stores metadata/storage_ref.

======================================================================
3. BACKEND IS AUTHORITATIVE
======================================================================

The backend/domain layer is authoritative for:

- PM due/overdue,
- PM remaining hours,
- PM remaining distance,
- calendar maintenance due,
- part lifetime due,
- remaining part lifetime,
- part usage accumulation,
- component transfer usage,
- certificate expiry,
- alert generation,
- device offline calculation,
- configuration sync status,
- remote command status,
- repair workflow status,
- inspection/finding workflow status.

Frontend pages display authoritative backend results.

Dashboard, Vehicle Detail, alerts, and reports must use the same domain services.

Do not independently reimplement the same PM/lifetime formula in multiple frontend pages.

======================================================================

from
physical vehicle identity.

ENGINE_MAIN

WORKING

5. ONE QR CODE PER CRANE
======================================================================

One crane = one permanent QR code.

The QR opens:

/vehicle/{vehicle_id}

The QR opens the main Vehicle Detail page.

It is NOT tied directly to inspection or another temporary workflow.

From Vehicle Detail, permission-dependent actions may include:

- inspection,
- repair reporting,
- PM,
- maintenance history,
- repair history,
- parts/lifetime information,
- driver/operator,
- certificates,
- documents,
- GPS,
- work history,
- IoT/device status.

Workshop equipment may use:

/equipment/{equipment_id}

One equipment item = one permanent QR code.

======================================================================
8. INSPECTION
======================================================================

User flow:

Scan QR
-> Detail page
-> ตรวจเช็ค
-> Complete checklist
-> ส่งผลการตรวจ

Inspection item may contain:

- title,
- inspection point,
- reference image,
- inspection method,
- acceptance standard,
- instructions,
- PASS,
- FAIL,
- N/A,
- remark,
- inspection photo.

Reference Image:
master image that explains what/where to inspect.

Inspection Photo:
evidence from the actual inspection.

These are separate concepts.

Checklist definitions are revision-controlled.

Historical results retain the exact checklist revision used.

Submitted inspection history must not be overwritten.

FAIL behavior:

- ordinary FAIL may create an abnormal finding for maintenance review,
- critical items may create an alert/repair path according to rules,
- do not automatically generate unnecessary Repair Orders for every minor issue.

======================================================================
11. PART TRACKING MODES
======================================================================

The platform must NOT require registration of every physical part on every vehicle from the beginning.

Support:

NONE
No individual lifetime tracking.

CONSUMABLE
Recorded when consumed during PM/repair.

POSITION_LIFETIME
Tracked by vehicle/position without unique physical instance for every unit.

INSTANCE_TRACKED
A physical reusable/transferable/high-value component with unique part_instance_id.

Same part name with different specification/size must be able to use separate part_id values.

======================================================================
12. INCREMENTAL PART REGISTRATION
======================================================================

Create part_instance only when it becomes necessary, for example:

- transfer between vehicles,
- replacement,
- start of lifetime tracking,
- high-value component,
- safety-critical component,
- reusable/repairable component.

Historical usage state:

KNOWN
PARTIAL
UNKNOWN

If unknown, do not estimate.

======================================================================
13. TRANSFERABLE COMPONENTS
======================================================================

Lifetime/usage follows the physical component.

Example:

Cylinder A
200/2
-> 200/1
-> IN_REPAIR
-> 200/2

Store usage segments with:

- part_instance_id,
- vehicle_id,
- component_id,
- position,
- installed_at,
- baseline counters,
- removed_at,
- ending counters,
- calculated usage,
- source work/event.

Time in IN_REPAIR does not accumulate vehicle operating hours.

======================================================================
14. REPAIR VS OVERHAUL
======================================================================

Normal repair does NOT reset lifetime automatically.

A major overhaul may start a new lifetime cycle only when an approved business rule defines it as a reset.

Old lifetime cycles remain in history.

16. COMPONENT-BASED COUNTERS
======================================================================

-> component_id

19. OFFLINE EVENT RECONCILIATION
======================================================================

= when the event happened

received_at
= when the backend received it

Also support:

event_id

device_id

time_quality

- duplicate protection,
- idempotency,
- delayed upload,
- out-of-order arrival,
- chronological history based on event_timestamp.

Do not sort work history only by received_at.

======================================================================
29. SAFETY-CRITICAL REMOTE FUNCTION
======================================================================

Safety command is separate from normal commands.

Future command may be:

REMOTE_INHIBIT

Requirements include:

- exact target vehicle/device,
- current model,
- online state,
- engine/PTO state when available,
- last seen,
- GPS when available,
- reason,
- short TTL,
- explicit confirmation,
- MFA/step-up authorization,
- command_id,
- ACK,
- execution state,
- physical feedback state,
- audit history,
- local reset/recovery policy.

Stale commands must not remain executable indefinitely.

Do not automatically execute old safety commands after reconnect/reboot.

Do not describe the feature as a certified E-Stop unless the complete engineered system qualifies.

======================================================================
30. MODEL-SPECIFIC EMERGENCY OUTPUT
======================================================================

The future ESP32 emergency-related output is a fixed ON/OFF timed sequence that may differ by crane model.

The user will provide authoritative existing code/timing later.

Rules:

- do not guess timing,
- do not allow ordinary Web editing of individual timing values,
- Web/backend may store approved profile metadata,
- model/profile compatibility must be enforced,
- actual waveform execution belongs to ESP32 firmware,
- physical feedback is separate from output activation.

34. POSTGRESQL MIGRATION PRINCIPLE
======================================================================

Google Sheets is the prototype schema and test data store.

The final design must map naturally to PostgreSQL.

Migration must validate:

- record counts,
- stable IDs,
- relationships,
- historical records,
- counters,
- PM,
- inspection,
- repair,
- part/lifetime history,
- IoT events,
- commands,
- audit.

After successful production migration:

Google Sheets should become archive/read-only.

Operational writes should go through Web/API to PostgreSQL.
