A07 Alert Deduplication / Auto-Resolve
Status: APPROVED / FROZEN (open-alert lifecycle contract only)
D25 (Web/API Phase 6 Batch 5B) freezes the internal alert lifecycle contract below. It is implemented as internal AlertService/Repository methods only — no HTTP mutation endpoint exists yet (see the "does NOT define" list at the end of this entry).

Open identity: an alert's identity is the tuple (vehicle_id, alert_type, source_type, source_id), compared by exact equality (None/blank matches None/blank only, never a wildcard).

Open statuses: ACTIVE, ACKNOWLEDGED, and MUTED are all "open". RESOLVED is the only closed status.

Duplicate reuse: creating a condition alert (`ensure_condition_alert`) first looks up existing rows (any status, full history) by identity. If exactly one open row already matches, that unchanged existing row is returned as-is (idempotent reuse) — its severity/message/created_at/alert_id are never overwritten by the new call's values. If zero open rows match, a new row is created using the caller-supplied alert_id (never generated by this decision — see A01). If MORE than one open row matches (only possible from the non-transactional Google Sheets write pattern already accepted project-wide — see A09 — racing calls can each pass the "no open row" check before either write lands), the service fails honestly with ALERT_OPEN_IDENTITY_CONFLICT rather than guessing which row is canonical.

Acknowledgement: ACTIVE -> ACKNOWLEDGED only. Idempotent: re-acknowledging an already-ACKNOWLEDGED alert is a no-op that preserves the original acknowledged_by_user_id/acknowledged_at (provenance of the FIRST acknowledgement, never overwritten by a later caller). MUTED -> ACKNOWLEDGED and RESOLVED -> ACKNOWLEDGED are both rejected.

Mute: ACTIVE -> MUTED or ACKNOWLEDGED -> MUTED, with a caller-supplied, timezone-aware, strictly-future muted_until — there is no default/implied mute duration. Idempotent only if the new call's muted_until exactly matches the already-stored value; a MUTED alert re-muted with a DIFFERENT muted_until is rejected rather than silently overwritten. RESOLVED -> MUTED is rejected.

Mute expiry reconciliation: a MUTED alert whose muted_until has passed transitions to ACKNOWLEDGED if it was ever acknowledged (acknowledged_at is set), otherwise back to ACTIVE. muted_until itself is preserved (never cleared) as a historical record of the mute that just expired. A MUTED alert with a missing/blank muted_until is corrupt persisted state and fails honestly rather than guessing an expiry.

Resolution: source-driven only — ACTIVE, ACKNOWLEDGED, or MUTED all transition to RESOLVED. Idempotent: resolving an already-RESOLVED alert is a no-op that preserves the original resolved_at.

No reopen: RESOLVED is terminal. Nothing in D25 transitions a RESOLVED alert back to any open status. Recurrence of the same underlying condition after resolution creates a BRAND NEW alert row with a new alert_id (via `ensure_condition_alert`'s normal "zero open rows match" path, since the resolved row is no longer open) — it never reopens or reuses the resolved row. Full history is retained; no row is ever deleted by this decision.

D25 does NOT define: alert_type -> severity mapping (still A06's own stated scope), the conditions under which any given alert_type is generated (PM due logic, DEVICE_OFFLINE timeout, sensor thresholds, etc.), the DEVICE_OFFLINE online/offline threshold itself (A05), alert_setting precedence or its auto_reenable_on_online column (note: auto_reenable_on_online is NOT the same thing as "auto-reenable on activity" — this decision does not equate the two), operational-status-based suppression, notification/escalation behavior, any public HTTP mutation endpoint or its RBAC (the live role_permission schema still has no alert-write permission — see M02), Phase 8 IoT-triggered alert generation, or Phase 9 OTA/safety-command alert behavior. Those all remain separately unresolved.

C04 Component Role Naming (Engine Roles)
Status: APPROVED / FROZEN (vocabulary only)
Approved Component Roles: CARRIER_ENGINE, CRANE_ENGINE, PTO.
CARRIER_ENGINE = engine used for the carrier / lower chassis / travelling
side of the crane. CRANE_ENGINE = engine used for the crane /
superstructure side. CARRIER_ENGINE and CRANE_ENGINE are
physical/functional roles, not first/second engine numbering.
A vehicle is not required to have both roles: valid combinations include
CARRIER_ENGINE only, CARRIER_ENGINE + PTO, CARRIER_ENGINE + CRANE_ENGINE,
or another valid combination supported by actual vehicle configuration.
Do not create a fake CRANE_ENGINE component for a machine that does not
physically have one.
ENGINE_MAIN and ENGINE_SECONDARY are deprecated legacy names and are not
valid authoritative roles for new data.
Counter types (ENGINE_HOUR, PTO_HOUR, ODOMETER) are a separate concept
from component role and remain unchanged by this decision.
This decision covers component-role vocabulary only; it does not resolve
any other open decision (including A02, A03, C01, C03).
See docs/phase-results/component-role-naming-correction.md.
